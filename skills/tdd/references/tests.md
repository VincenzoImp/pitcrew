# Good and bad tests

The examples are TypeScript-like for brevity. The rules hold in any language.

## Behaviour, not implementation

```typescript
// GOOD: checks what callers care about, through the public interface
test("user can check out with a valid cart", async () => {
  const cart = createCart();
  cart.add(product);
  const result = await checkout(cart, paymentMethod);
  expect(result.status).toBe("confirmed");
});

// BAD: checks how the code works inside
test("checkout calls paymentService.process", async () => {
  const mockPayment = jest.mock(paymentService);
  await checkout(cart, payment);
  expect(mockPayment.process).toHaveBeenCalledWith(cart.total);
});
```

Warning signs of a test coupled to the implementation:

- it mocks your own collaborators;
- it tests private functions;
- it asserts on call counts or call order;
- it breaks when you restructure without changing behaviour;
- its name says how, not what.

## Verify through the interface

```typescript
// BAD: goes around the interface to check
test("createUser saves to database", async () => {
  await createUser({ name: "Alice" });
  const row = await db.query("SELECT * FROM users WHERE name = ?", ["Alice"]);
  expect(row).toBeDefined();
});

// GOOD: checks through the interface
test("a created user can be read back", async () => {
  const user = await createUser({ name: "Alice" });
  const retrieved = await getUser(user.id);
  expect(retrieved.name).toBe("Alice");
});
```

## Independent expected values

```typescript
// BAD: tautological; the expected value is computed the way the code computes it
test("calculateTotal sums line items", () => {
  const items = [{ price: 10 }, { price: 5 }];
  const expected = items.reduce((sum, i) => sum + i.price, 0);
  expect(calculateTotal(items)).toBe(expected);
});

// GOOD: a known literal
test("calculateTotal sums line items", () => {
  expect(calculateTotal([{ price: 10 }, { price: 5 }])).toBe(15);
});
```

The same trap in other forms: a snapshot written by running the code and never checked by hand; a
fixture generated by the function under test; a constant compared with itself.

## Check the outcome, not the calls

```typescript
// GOOD: the result
it("returns tasks newest first", async () => {
  const tasks = await listTasks({ sortBy: "createdAt", sortOrder: "desc" });
  expect(tasks[0].createdAt.getTime()).toBeGreaterThan(tasks[1].createdAt.getTime());
});

// BAD: the query text
it("calls db.query with ORDER BY created_at DESC", async () => {
  await listTasks({ sortBy: "createdAt", sortOrder: "desc" });
  expect(db.query).toHaveBeenCalledWith(expect.stringContaining("ORDER BY created_at DESC"));
});
```

## One behaviour per test, named for it

```typescript
// GOOD
it("rejects an empty title", () => { ... });
it("trims spaces around the title", () => { ... });

// BAD: three behaviours, one vague name; the first failure hides the others
it("validates titles correctly", () => {
  expect(() => createTask({ title: "" })).toThrow();
  expect(createTask({ title: "  hello  " }).title).toBe("hello");
  expect(() => createTask({ title: "a".repeat(256) })).toThrow();
});
```

Only write the three tests if all three behaviours are risky. A length limit enforced by a schema
library needs no test of its own.

## Anti-patterns

| Anti-pattern | Why it hurts | Instead |
| --- | --- | --- |
| Coupled to the implementation | breaks on refactor, catches no bug | test inputs and outputs at the seam |
| Tautological | passes by construction | independent expected values |
| Horizontal slicing (all tests first) | tests imagined behaviour | one test, then its code |
| Testing the framework or a library | tests someone else's code | test only your behaviour |
| A test per function or per file | many tests, little protection | a test per risky behaviour |
| The same path at three levels | triple cost, one protection | test it at the highest useful seam |
| Large unread snapshots | break on any change, nobody reviews them | small, explicit expected values |
| Shared state between tests | pass alone, fail together | each test builds its own state |
| Real time, random or network | flaky | inject or fix them at the boundary |
| Shared setup that hides the story | reader must trace helpers | a little repetition in the test body |
| Mocking everything | green tests, broken product | real code, then fakes, then stubs |
| Tests for a coverage target | tests that check nothing | tests for risk |
